## Findings

### F1. Signup failure is a separate event and signup has no outcome event to hold status + failure_reason
**Medium.** _Confirmed by the verifier._
signup_form_submitted fires at the start of the handler (intent only). The only outcome signal is signup_form_submit_error, fired from the catch block, so failure lives on its own event (rule 4) and success has no event. 'How many signup attempts fail' needs a union of the two events and can't give a success rate. The catch also skips several end states: the Cloudflare invalid-token error returns silently, as do user-already-exists, checkout-session redirect and account-under-review. These attempts have an intent event and no outcome, so they look like abandonment in a funnel.
- **Evidence:** `apps/web/modules/signup-view.tsx:243`, `apps/web/modules/signup-view.tsx:261`, `apps/web/modules/signup-view.tsx:282`, `apps/web/modules/signup-view.tsx:322`, `apps/web/modules/signup-view.tsx:326`
- **Fix:** Add one outcome event (e.g. signup_completed) with status = success | failed | cancelled and failure_reason (enum). Use values read from the code: user_already_exists, invalid_cloudflare_token, checkout_required, under_review, api_error, sign_in_failed. Do not rename signup_form_submit_error in place. Dual-fire both events for one release (dual_fire_until on the old entry), then mark the old entry deprecated with deprecated_reason and replaced_by. Add a SEMANTICS changelog line. Dashboards on this event's question 'How many signup attempts fail, and why?' move to the new event.
- **Items:** `signup_form_submit_error`
- **Verifier:** Read `apps/web/modules/signup-view.tsx` lines 240–335 and searched the repo for any other signup `capture` call (none, apart from the three button clicks). - `signup_form_submitted` fires before the request at :243. The only outcome is `signup_form_submit_error` in the catch at :326, and no event fires on success, so the success rate can't be measured. Several paths end with no outcome event: user already exists (:262–268), the checkout redirect (:271–279), account under review (:285–287) and the Cloudflare invalid-token error (:322–323). They will look like abandonment. Correction for the fix: in `calcomSignupHandler.ts` the checkout case ("Created user but missing payment", :319) and the under-review case (:303) both come after the user has been created. They are not failures, so they should not be `failure_reason` values. Record them as success with a separate dimension, such as `next_step = checkout | under_review`.

### F2. error_message sends raw free text from the server or client as the failure reason
**Medium.** _Confirmed by the verifier._
error_message is the thrown Error's message. That is result.error.message from the signup API, or a translated UI string. It is unbounded, localized free text, so the same failure splits into many values in a breakdown. Its content is not controlled by the plan, so it could include user-supplied values. The catch also treats an exception from signIn as a signup failure, and the handler doesn't distinguish the two sources.
- **Evidence:** `apps/web/modules/signup-view.tsx:282`, `apps/web/modules/signup-view.tsx:320`, `apps/web/modules/signup-view.tsx:331`
- **Fix:** Replace error_message with a closed failure_reason enum on the new outcome event, mapped from API error codes or the failing step (signup request vs. sign-in). Keep the raw message out of analytics and leave it in the form error and server logs. If you keep a message for debugging, truncate it and mark the values you haven't observed as (UNCONFIRMED).
- **Items:** `signup_form_submit_error`
- **Verifier:** Read :282, :320 and :331, plus the signup API handlers that produce `result.error.message`. - `error_message` is free text: whatever message the server sends back, a translated fallback, or any error thrown by `signIn`. It is not a closed list. Correction: the text is mostly not localized. The server sends fixed English strings ("Invalid username", "Username or email is already taken", "A user exists with that username", "Signup is disabled", "Internal server error"). The translated `unexpected_error_try_again` text is used only when the thrown value isn't an `Error`. So the breakdown splits less than the finding says. `route.ts:72` passes through an arbitrary `e.message` from `HttpError`, so I can't rule out user-supplied content, but I can't confirm it either. The closed-enum fix still applies, and its values can come from the server strings above.

### F3. verify_email_already_verified can fire again when feature flags change, and may read onboarding_v3_enabled before flags load
**Low.** _Confirmed by the verifier._
The event sits in an effect that depends on `[data?.isVerified, flags]`. Once the user is verified, it fires every time the `flags` object changes identity, for example when flags load or refresh. The redirect still runs the first time, but the page can send the event more than once for one visit. If the first run happens before flags are populated, `onboarding_v3_enabled` is undefined and the redirect goes to the wrong path. This inflates the already-verified count and can leave the flag property empty or wrong.
- **Evidence:** `apps/web/modules/auth/verify-email-view.tsx:50`, `apps/web/modules/auth/verify-email-view.tsx:57`
- **Fix:** Fire the event once, for example with a ref guard (`hasTracked.current`). Wait until flags are loaded before reading `flags["onboarding-v3"]`. Alternatively, depend only on `data?.isVerified`.
- **Items:** `verify_email_already_verified`
- **Verifier:** Read `verify-email-view.tsx` lines 46–57, `useFlagMap` (`packages/features/flags/context/provider.ts`) and `useFlags` (`apps/web/modules/feature-flags/hooks/useFlags.ts`). - The flags object is `query.data ?? initialData`. When the tRPC query resolves, `flags` becomes a new object and the effect runs again. A verified user can therefore send the event twice and get two `router.replace` calls, as long as the page is still mounted when the flags arrive. Correction: before the flags load, `flags["onboarding-v3"]` is `false`, not `undefined`, because `initialData` sets it to `false`. So the first event can report `false` when the flag is really on, and the first redirect goes to `/getting-started`; the second run then redirects to the right path. The registry description ("may be undefined if the flags have not loaded") is wrong in the same way and should say "false until flags load". A later refetch that returns the same data probably keeps the same object, because React Query's structural sharing reuses unchanged data, so the "refresh" part of the finding is unlikely in practice.
